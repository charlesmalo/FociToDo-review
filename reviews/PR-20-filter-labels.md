# Review — PR #20: fix(web): name each filter control by its label alone

- App commit range: `3b76cfa..5c43da9` (one commit, `a524a3d`; merged as `5c43da9c1490a28e17daf8842e0e01958b737ad1`) · PR: https://github.com/charlesmalo/FociToDo/pull/20 · Date: 2026-10-03 · Reviewer: Claude Code (automated) + solution-lead triage
- Origin: not a planned PR. The companion review repository's new independent **storyboard** harness, driving the real app with Playwright/Chromium, found that each filter `<select>`'s accessible name included every one of its options. Recorded as **F-92**.

## Automated review output

Scope of PR #20 (one commit, `a524a3d`; `apps/web/src/todos/components/TodoFilters.tsx` and its test only).

**Root cause (independently re-read, not trusted on the report's word)**: `TodoFilters.tsx` nested each `<select>` directly inside its `<label>` (`<label>Sort by<select>...</select></label>`). A real browser's accessible-name computation (per the HTML/ARIA accname algorithm) for a `<label>`-wrapped control uses the label's **entire text content**, including the content of descendant elements — so Chromium computed the "Sort by" control's accessible name as `"Sort by Created Due date Title"` (the caption plus every `<option>`'s text). This is exactly the browser behaviour the HTML spec describes for implicit labels; it was not caught earlier because **jsdom's accessible-name library does not reproduce it** — the app's own component/unit tests run under jsdom, so `TodoFilters.test.tsx`'s existing role-name assertions passed throughout. Only a real-browser harness (this review's storyboard, Playwright driving actual Chromium) could find this — exactly the kind of gap independent acceptance/storyboard is meant to close.
- Secondary symptom: the inflated accessible names created a Playwright strict-mode locator ambiguity between the "Sort by" control and the dialog's own "Title"/"Due date" fields — the same ambiguity two existing e2e tests had already worked around by scoping their locators to the dialog (F-41, accepted at PR #9; not a cause, but a related symptom of the same root defect, now fixed at the source instead of only worked around at the call site).

**The change**:
- `<label htmlFor={id}>Caption</label>` beside a separate `<select id={id}>`, with each `id` generated by `useId()` so it's unique and stable per component instance; each label/select pair sits in its own `.field` wrapper so the visual layout is unchanged (confirmed by the storyboard's filter-and-sort frames, screenshot-identical placement).
- The outer `role="group"` "Filter and sort" wrapper (`aria-labelledby`) is unchanged.
- New structural regression test: asserts each `<select>`'s associated `<label>` element's text is **exactly** its caption (`"Show"`, `"Sort by"`, `"Order"`) — a DOM-structure assertion, not an accessible-name computation, since jsdom's accname library can't reproduce the browser behaviour that caused the bug. The existing role-name assertions are kept as guards, not as the regression test itself.

**Verification (independently re-read)**:
- RED (pre-fix): computed label text was `"ShowAllCompletedIncompleteOverdue"` / `"Sort byCreatedDue dateTitle"` / `"OrderAscendingDescending"` — matches the storyboard's own finding.
- GREEN (post-fix): each label's text is exactly its caption.
- Full gate: 459 tests, coverage 100%; e2e 8/8; a screenshot shows the filters render identically (no visual regression).

**Independent re-confirmation by this review's own storyboard run on the merged commit `5c43da9`** (this sign-off cycle): 22 frames across 11 journeys, all 13 wireframes paired, including the `filter-and-sort` journey's frames against the fixed controls — [`evidence/2026-10-03T090448Z/storyboard/storyboard.md`](../evidence/2026-10-03T090448Z/storyboard/storyboard.md).

**No new findings beyond F-92.** The fix addresses the actual accname root cause (label structure), not merely the locator symptom; the new regression test is correctly aimed at the DOM structure the browser's algorithm reads, with an honest note about why jsdom's own accessible-name computation can't be the regression guard here.
